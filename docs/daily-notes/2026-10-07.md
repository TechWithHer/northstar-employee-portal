**Status:** WORKING

### Infrastructure Layer — WORKING WITH DESIGN LIMITATIONS

- VPC exists.
- Public subnet exists.
- Private subnet exists.
- Internet Gateway exists.
- Public and private route tables exist.
- House EC2 is running with both public and private IPv4 addresses.
- Warehouse EC2 is running with both public and private IPv4 addresses.
- Warehouse is associated with a private subnet whose route table contains only the VPC local route.
- No NAT Gateway currently exists.

**Observation:**
Warehouse has a public IPv4 address even though the database tier does not require public addressing. Its subnet has no route to an Internet Gateway, so the public IP alone does not provide internet connectivity.

**V2 consideration:**
The database tier should remain private and should not receive a public IP.

**Status:** WORKING WITH DESIGN LIMITATIONS

### Security Layer — WORKING WITH SECURITY LIMITATIONS

#### Inbound
- House allows HTTP (TCP/80) from the internet.
- House allows SSH (TCP/22) from the internet.
- Warehouse allows MySQL (TCP/3306) only from resources associated with the House security group.
- Warehouse does not expose MySQL directly to the internet.

#### Outbound
- Both security groups currently allow all outbound traffic.
- Outbound Security Group permission alone does not guarantee connectivity; a valid network route is also required.
- Warehouse currently has no default internet route despite its permissive outbound Security Group.

#### Observations
- Public SSH access to House increases the attack surface and should be removed in V2.
- Egress rules can be reviewed and restricted where there is a clear requirement without making the infrastructure unnecessarily brittle.
- Security Groups are stateful, so response traffic for an allowed connection is automatically permitted.

**V2 considerations:**
- Application instances should not expose SSH directly to the internet.
- Review egress requirements separately for the application and database tiers.
- Keep database access limited to the application tier.

**Status:** WORKING WITH SECURITY LIMITATIONS

### IAM & Secrets Management — WORKING

- House uses the `Northstar-House-App-Role` IAM role for AWS authentication.
- No static AWS credentials file was found under `~/.aws/credentials`.
- The IAM role can retrieve the `northstar/prod/database` secret from AWS Secrets Manager.
- Database credentials are not stored directly in the application code.
- Secrets Manager access was verified without exposing the secret value.

**Observation:**
Application database connectivity depends on successful Secrets Manager access.
Removing `secretsmanager:GetSecretValue` would prevent the application from retrieving database credentials and could result in an HTTP 500 response.

**Status:** WORKING

### CI/CD — WORKING WITH DESIGN LIMITATIONS

- GitHub Actions is triggered by pushes to the `main` branch.
- CI application validation completed successfully.
- CD deployment to House completed successfully.
- Deployment currently uses SSH from a GitHub-hosted runner to House.

#### Issue observed during audit
- CD initially failed during the SSH configuration step.
- House's public IPv4 address had changed, making the `EC2_HOST` GitHub secret stale.
- Updating the deployment configuration restored the pipeline successfully.

#### V2 considerations
- Deployment should not depend on a mutable EC2 public IP.
- Application instances should not require public SSH access for deployment.
- A production-oriented deployment mechanism should target private application infrastructure without exposing SSH to the internet.

**Status:** WORKING WITH DESIGN LIMITATIONS

- Alarm: `Northstar-House-High-CPU`
- Metric: `CPUUtilization`
- Threshold: CPU > 70%
- Evaluation period: 5 minutes
- Datapoints to alarm: 1 out of 1
- Current alarm state during audit: OK.
- Alarm notifications are connected to the `Northstar_CPU_Alarm` SNS topic.

#### Observations
- V1 provides basic infrastructure-level CPU monitoring and email alerting.

#### V2 considerations
- Add application health monitoring.
- Centralize application and service logs.
- Review alarm thresholds and evaluation periods based on expected workload.
- Expand monitoring beyond CPU to cover relevant infrastructure and application signals.

### Key V1 Problems Identified

1. **Application Tier Has Direct Internet Exposure**
   - House is directly internet-facing.
   - SSH is exposed to the internet.
   - CI/CD depends on direct SSH access and a mutable public IP.

2. **Database Tier Requires Stronger Isolation and Lifecycle Management**
   - Warehouse receives a public IP even though the database does not require public exposure.
   - The database tier currently has no controlled outbound path for activities such as system/package updates.
   - Database availability, maintenance and resilience depend on a single EC2-hosted MySQL instance.

3. **Monitoring and Observability Are Limited**
   - Monitoring currently focuses primarily on EC2 CPU utilization.
   - Application health is not monitored directly.
   - Application/service logs are not centralized.
   - Broader infrastructure and application signals are not yet covered.

4. **Single Points of Failure**
   - The application currently depends on a single application EC2 instance.
   - The database depends on a single MySQL EC2 instance.
   - There is no automatic application instance replacement or multi-AZ application design.
   - Database failover is not automated.

## Architecture Decisions

- Northstar V2 will use two Availability Zones within a single AWS Region.
- Multi-AZ is being used primarily for high availability and fault isolation.
- Multi-region disaster recovery is outside the current V2 scope.
- V2 will separate the network into three tiers:
  - Public
  - Private Application
  - Private Database
- Each tier will have one subnet per Availability Zone, resulting in six subnets.
- Public subnets can share one public route table because their routing requirements are identical.
- Application and database tiers will use separate private routing strategies.
- Resources in private App and DB subnets will not receive public IPv4 addresses.
- NAT Gateway has not been selected yet. Outbound requirements will be evaluated before choosing NAT, VPC endpoints, or another approach.

## What I Learned

- Multi-AZ primarily addresses high availability; multi-region architectures are commonly used for broader disaster recovery requirements.
- An EC2 public IP alone does not make an instance internet reachable.
- A subnet is public because its route table provides a route to an Internet Gateway.
- Subnets in different AZs can share a route table when their routing requirements are identical.
- Security Group permission does not create network connectivity; routing must also provide a valid path.
- Public-facing ALB allows application instances to remain private.
- Private application and database tiers may require different outbound routing policies.
- Architecture decisions should start from requirements and observed problems rather than selecting AWS services first.
